# ADR 0002 — Themed glyphs reach QSS `image:` as rasterised PNGs, not SVGs

Status: accepted · 2026-09-03 · supersedes nothing · consumed by 9.0, 9.4, 9.5

## Context

Phase 9 needs Lucide glyphs inside QSS sub-controls that Qt draws itself and
that no delegate owns: `QCheckBox::indicator`'s tick (9.5) and
`QHeaderView::up-arrow`/`::down-arrow`'s sort caret (9.4). QSS reaches those
through the `image:` property, which takes a `url()` and nothing else — it
accepts no colour, so a glyph handed to it must arrive already the right
colour, in both themes.

`shared/icons.py` (moved from `gui/icons.py` in 9.0) solves colouring for
`QIcon` consumers by substituting Lucide's `stroke="currentColor"` in the SVG
*source* and rendering through `QSvgRenderer`. Its docstring records why that
matters beyond crispness: nothing ever loads an `.svg` through `QIcon` or
`QPixmap`, **so the frozen build does not depend on Qt's `qsvg` imageformats
plugin being collected**. That plugin is a PyInstaller collection hazard — it
is loaded by name at runtime, is invisible to static analysis, and its absence
degrades silently to a blank image rather than an error.

The obvious implementation, `image: url(check.svg)`, quietly reverses that
decision: `image:` resolves through `QImageReader`, so an SVG there *is* a
`qsvg` dependency. The question is what to hand `image:` instead.

## Options measured

Probed on PySide6 6.11.1, offscreen, by rendering a checked `QCheckBox` and
counting distinct pixel colours in the indicator (8 = nothing drew; 25 = the
antialiased glyph drew).

| Option | Result | Verdict |
|---|---|---|
| `url(<file>.svg)` | 25 — draws | Works, but **is** the `qsvg` dependency |
| `url(data:image/svg+xml;base64,…)` | 8 — nothing drew | Qt's QSS `url()` does not parse data URIs |
| `.qrc` resource | not probed | Needs a compile step and bakes colour in at build time; two themes × N glyphs regenerated by hand |
| Custom-painted widgets, no `image:` | n/a | Replaces three QSS rules with three widget subclasses |
| **`url(<file>.png)`, rasterised by `QSvgRenderer` at runtime** | **25 — draws, pixel-identical to the SVG** | **chosen** |

The winner reuses the machinery already in `shared/icons.py` — same
`currentColor` substitution, same `QSvgRenderer`, same cache-on-inputs
discipline. The only new step is `QPixmap.save()`. `QtSvg` is already linked
and already collected, because `icon()` imports it; the *plugin* is what stays
uncollected.

## Decision

`shared/icons.py` grows one function beside `icon()`:

```python
def glyph_url(name: str, color: str | None = None, size: int = 18) -> str:
    """A QSS-ready `url("…")` token for a themed glyph."""
```

It substitutes the colour into the SVG source, renders one `QPixmap` at
`size`, writes it under `QStandardPaths.CacheLocation / "glyphs"` as
`<name>-<8 hex of the recoloured source>-<size>.png`, and returns
`url("<posix path>")`. The content hash in the filename means a re-vendored
Lucide glyph or a retuned token invalidates its own cache entry; nothing else
does, so the file is written once and reused for the life of the install.

Colour is part of the filename, so a theme toggle needs no invalidation — it
misses into a second set of entries, exactly as `icon()`'s `@cache` does.
`build_stylesheet(theme)` interpolates the token, and every app already
rebuilds its sheet on toggle.

**The path must be spelled with `Path.as_posix()`.** Measured on the same
probe: a backslash-spelled path draws nothing, quoted or not, while a path
containing spaces is fine either way. `str(Path)` on Windows produces
backslashes, so the naive spelling is a silent, Windows-only, production-only
blank glyph. This is asserted by a test, not by a comment.

## Consequences

- Two rendering routes for one glyph set: `icon()` for `QIcon` consumers,
  `glyph_url()` for QSS `image:`. Both read the same SVGs and the same tokens,
  and both rasterise through the same `_pixmap()` helper, so they cannot drift
  in appearance — only in call site.
- **`glyph_url()` writes one resolution; `icon()` writes four.** `icon()`
  hands `QIcon` a pixmap at each of `_RENDER_SIZES` so Qt can pick the one
  matching the screen's device pixel ratio; a QSS `image:` url has no such
  ladder, so `glyph_url(size=18)` is an 18px raster and a 150%-scaled warehouse
  PC upscales it. Not fixed here, because 9.0 has no call site to measure:
  the whole point of the PNG route is that a caller can be added without
  reopening this decision. **If 9.4 or 9.5 sees a soft caret or checkmark, the
  fix is Qt's `@2x` filename convention** — write `<name>-<sha>-<size>@2x.png`
  at `size * 2` beside the 1x and Qt's stylesheet image loader picks it up.
  That is a change inside `glyph_url()`, invisible to its callers.
- The app writes files to the user cache directory at startup. Small (a
  186-byte PNG at 18px), bounded by glyphs × colours × sizes, and a wiped cache
  directory self-heals on the next paint.
- `image:` is now available to any future sub-control without reopening this
  question. 9.4 and 9.5 consume it; neither invents its own scheme.
- If a later Qt release teaches QSS `url()` to read data URIs, the file writes
  become removable without changing a single call site.
- **A glyph cannot go on `QHeaderView::section`** (measured 2026-09-04,
  PySide6 6.11.1, offscreen). Bundle 3's 9.4 wanted a hover sort caret and its
  plan prescribed `QHeaderView::section:hover { image: … }`. A throwaway probe
  rendered a three-column header with and without that rule and counted
  non-background pixels: **7172 → 5368**. The `image:` is drawn *instead of*
  the section's label, not beside it — hovering a header would blank its
  title. `background-image` with `background-repeat`/`background-position`
  fails the same way (7172 → 1215, and the glyph never appears). Both spellings
  were tried; neither ships. The sort-indicator sub-controls
  `QHeaderView::up-arrow` / `::down-arrow` *do* take a `glyph_url()` and leave
  the label intact — but they render only on the sorted section, which is the
  half Qt already gets right. So the hover caret is not buildable in QSS at
  all, and 9.4 ships without it; see the Bundle 3 spec §4.5.

## What this does not decide

Whether a given sub-control needs a *glyph* at all. A radio dot and a toggle
knob are circles, and QSS draws circles with `border-radius` — those get no
SVG. See the 9.0 spec, § "The glyph inventory".
