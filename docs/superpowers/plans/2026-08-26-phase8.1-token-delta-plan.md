**Goal:** Close the live 2.90:1 AA failure on `main` (`button_hover_dark #2D9FE8` behind
white) by adding the three missing tokens and making `validate_theme` prove `on_accent`
against *every* accent fill and every foreground against *every* surface plane.

**Architecture:** All six token edits happen in **`packing-tool/shared/theme.py`**, which
owns `shared/`. `shopify-fulfillment-tool` receives them by running
`python scripts/sync_shared.py <packing-tool-path>` and adds a guard test over the synced
result. The fix that matters is not the two hexes — it is turning two single-value
assertions in `validate_theme` into loops, so the *class* of bug cannot ship again.

**Tech Stack:** Python 3, `dataclasses` (frozen `ThemeTokens`), pytest, PySide6 (only as
the consumer of `build_stylesheet` / `build_palette`; no Qt code changes here).

**Spec:** `docs/superpowers/specs/2026-08-26-phase8-unified-design-system.md`
— §3 is the complete change list, §2/C1 and §2/C4 carry the measured ratios,
§7 tests 1 and 2 are the acceptance criteria.
**Roadmap:** `docs/superpowers/plans/2026-08-26-phase8-roadmap.md` §2 → 8.1.

## Global Constraints

Copied verbatim from the spec and the roadmap. Every task below inherits these.

1. **`shared/theme.py` is authored in `packing-tool`.** Editing
   `shopify-fulfillment-tool/shared/theme.py` by hand is a defect — the next
   `sync_shared.py` silently overwrites it. Roadmap §3.1.
2. **Never re-derive a hex.** Every value below is quoted from the spec with a measured
   ratio. A step that computes a colour is off-plan; re-read the spec instead. Roadmap §3.3.
   This includes the six widened light foregrounds: they were derived and approved at
   Stage A and now live in spec §2/C1's amendment, so Stage B copies them like any other.
3. **The ten frozen aliases are read-only.** `background`, `background_elevated`,
   `accent_blue`, `accent_green`, `accent_orange`, `accent_red`, `active_background`,
   `active_border`, `button_hover_light`, `button_hover_dark`. Existing call sites may keep
   reading them until 8.3; **no new call site may.** Roadmap §3.2. "Read-only" freezes what
   an alias *points at*, not the value it carries: constraint 5 forces an alias's literal to
   track its canonical token, which is why `background`, `accent_green`, `accent_orange` and
   `accent_red` all change value in this task without breaking the freeze.
4. **Colour fields carry no dataclass defaults.** `tests/test_theme.py::
   test_every_colour_field_is_declared_per_theme_not_defaulted` enforces it — the three new
   tokens must be spelled out in *both* `LIGHT_THEME` and `DARK_THEME`, even the two that
   are theme-independent.
5. **Aliases must equal their canonical token.** `validate_theme` asserts it, so any change
   to `surface` must be mirrored into `background` in the same edit.
6. **Both repos' local `main` is stale.** Branch from `origin/main`, never local `main`.
   Verified 2026-08-26: packing local `main` was 4 commits behind `origin/main`.
7. Gate before finishing, in **both** repos:
   `QT_QPA_PLATFORM=offscreen python -m pytest` and `ruff check .`
   (shopify adds `--exclude shared`).

### Two decisions made at Stage A (do not re-litigate)

**D1 — both `button_hover_*` aliases point at `accent_fill_active`, not `accent_fill_hover`.**
Spec §2/C4 says the two aliases are re-pointed at the new fills but does not say which. The
roadmap's Stage C instruction settles it: *"confirm the alias re-point is a no-op in light
theme (`button_hover_light` was already `#005A9E`)"*. `#005A9E` **is** `accent_fill_active`,
so `accent_fill_active` is the only mapping under which light theme does not move.
Consequence: `accent_fill_hover` lands with **no consumer yet** — 8.5's four-variant button
hierarchy is what will read it, exactly as `surface_sunken` waits for 8.6's nav rail.
Consequence in dark theme: a primary button's hover goes *darker* (`#006FBA` → `#005A9E`)
instead of lighter, matching what light theme already does. That is the AA fix.

**D2 — `build_stylesheet` is not touched.** It reads `button_hover_light` / `button_hover_dark`
today; those are frozen aliases and constraint 3 lets existing call sites keep reading them
until 8.3. Re-pointing the aliases fixes the rendered colour without touching a QSS line, so
the diff stays a pure token change. Migrating `:hover` → `accent_fill_hover` and `:pressed`
→ `accent_fill_active` belongs to 8.5, where the button hierarchy makes it meaningful.

### What the new planes cost the existing floors (measured, not reasoned)

Adding `surface_sunken` to the plane matrix widens every foreground assertion. An earlier
draft of this plan argued the new planes were safe by monotonicity. **That argument was
wrong for light theme and is deleted.** Contrast is
`(L_lighter + 0.05) / (L_darker + 0.05)`; in light theme the *background* is the lighter
side, so darkening a light plane **lowers** contrast against dark foregrounds. Monotonicity
only ever favoured dark theme, which is the case the spec had actually measured. Never
substitute that reasoning for a measurement again — every plane change below is measured.

- **Dark `surface_sunken #08080B`** is darker than the old `#0A0A0A`, and dark theme's
  foregrounds are the *lighter* side, so this genuinely does raise contrast. Measured
  anyway: `text` 17.87, `text_secondary` 9.22. Both clear.
- **Dark `surface #0A0A0A` → `#101014`** costs ratio. Spec §2/C1 measured all eight affected
  foregrounds; worst case `text_disabled` at 3.72 against a 3.0 floor. All clear.
- **Light `surface_sunken #E8E8EB`** costs ratio, and six shipped tokens fall short — by
  0.02–0.08, because they were tuned to exactly clear `surface_overlay #EAEAEC`, light's
  previous darkest plane and the binding one per the in-file comment. Resolved at Stage A
  (spec §2/C1, amended): **the plane stays put and the six foregrounds widen to meet it.**

| token | from | to | on `#E8E8EB` | floor |
|---|---|---|---|---|
| `text_placeholder` | `#6A6A6A` | `#686868` | 4.56 | 4.5 |
| `border` | `#868686` | `#858585` | 3.02 | 3.0 |
| `status_info` | `#006DB7` | `#006BB5` | 4.55 | 4.5 |
| `status_success` | `#347736` | `#337635` | 4.54 | 4.5 |
| `status_warning` | `#995B00` | `#985A00` | 4.52 | 4.5 |
| `status_danger` | `#D0190B` | `#CF180A` | 4.53 | 4.5 |

Each is the minimum darkening that clears its floor — one to two sRGB units per channel,
below any perceptual threshold. `validate_theme` was run against these values with all four
planes in place: light PASS, dark PASS. Every other light foreground already clears
`#E8E8EB` with room (`text` 14.23, `text_secondary` 5.64, `text_disabled` 3.23, `focus_ring`
5.03, `selection_border` 4.44).

**D3 — the three legacy colour aliases move with them.** `accent_green`, `accent_orange`
and `accent_red` are `_ALIAS_PAIRS` entries for `status_success` / `status_warning` /
`status_danger`; the alias-drift check runs *before* the contrast loops and will fail loudly
if they are left behind. Changing their value is not re-pointing them, so Global Constraint
3 ("legacy aliases are read-only until 8.3") is not violated. `selection_border` and
`active_border` only coincidentally share `#006DB7` with `status_info` — they are **not**
aliased to it, they stay at `#006DB7`, and they still clear their 3.0 floor at 4.44. Do not
"fix" that two-unit divergence.

from shared.theme import (
    _SURFACE_PLANES,
    DARK_THEME,

```python
@pytest.mark.parametrize("theme", [LIGHT_THEME, DARK_THEME], ids=["light", "dark"])
@pytest.mark.parametrize("fill", ["accent_fill", "accent_fill_hover", "accent_fill_active"])
def test_white_still_clears_aa_on_every_button_fill(theme, fill):
    """spec 7 test 2. gui/*.py paints white on the accent fill and Qt swaps
    the hover and pressed fills in behind the same label. A sync that
    re-pointed any of the three would drop a primary button below AA
    silently -- 2.90:1 is exactly what shipped before 8.1."""
    assert contrast_ratio(theme.on_accent, getattr(theme, fill)) >= 4.5


def test_the_sync_brought_the_fourth_plane_with_it():
    """spec 7 test 1. surface_sunken has no call site in this repo until 8.6,
    so nothing else here would notice if a sync dropped it -- and the
    four-plane contrast sweep inside validate_theme silently narrows back to
    three when it goes."""
    assert len(_SURFACE_PLANES) == 4
    assert "surface_sunken" in _SURFACE_PLANES
    for theme in (LIGHT_THEME, DARK_THEME):
        assert theme.surface_sunken != theme.surface


def test_the_hover_aliases_carry_an_aa_safe_fill():
    """~180 call sites in gui/*.py still read button_hover_light/dark by
    name (they are frozen until 8.3). Whatever they resolve to has to carry
    white text, because that is what QPushButton paints on them."""
    for theme in (LIGHT_THEME, DARK_THEME):
        assert contrast_ratio(theme.on_accent, theme.button_hover_light) >= 4.5
        assert contrast_ratio(theme.on_accent, theme.button_hover_dark) >= 4.5
```
