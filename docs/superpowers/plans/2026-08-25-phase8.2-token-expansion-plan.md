# Phase 8.2 — Token expansion in `shared/theme.py` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to
> implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> The roadmap runner's Stage B declines `subagent-driven-development` — stay in-session.

**Goal:** Give `ThemeTokens` the full colour/spacing/radius vocabulary fixed by the 8.1
design-system spec, repair light mode's three failing status colours, and make the WCAG
contrast matrix a machine-checked property of the theme rather than a claim in a document.

**Architecture:** All edits land in `packing-tool/shared/theme.py` (the canonical copy) and
are then copied into this repo by `scripts/sync_shared.py`. Every change is additive at the
call-site level: existing field names survive as real dataclass fields aliasing the new
canonical ones, so ~180 `theme.<field>` reads across `gui/*.py` keep working untouched and
pick up the new values for free. The contrast maths lives in `shared/theme.py` itself —
not in a test file — so the check syncs to both repos instead of being duplicated in two
test suites that can drift apart.

**Tech Stack:** Python 3, `dataclasses` (frozen), PySide6, pytest. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-08-25-phase8.1-design-system-design.md` (merged in
PR #293). §3 is the value table, §6 is the acceptance criterion.

## Two corrections to the spec, already resolved

Record these in the PR description; they are deviations from §3 made deliberately.

**1. Light `text_disabled` and `text_placeholder` fail their own stated floors on the raised
and overlay planes.** §3.2's table measures text against `surface` only, while §3.1
introduces three planes and §6 makes the overlay plane binding for `status_*` and `border`.
The text scale was never re-measured against it. Verified:

| token | spec value | on `surface` | on `surface_raised` | on `surface_overlay` | floor |
|---|---|---|---|---|---|
| `text_disabled` | `#949494` | 3.03 | **2.76** | **2.52** | 3.0 |
| `text_placeholder` | `#767676` | 4.54 | **4.13** | **3.78** | 4.5 |

Disabled controls and placeholder text live on cards and in dialogs, which is precisely
where they fail. Corrected values (greys, same hue, lightness only):

| token | new light value | on `surface` | on `surface_raised` | on `surface_overlay` |
|---|---|---|---|---|
| `text_disabled` | `#808080` | 3.95 | 3.59 | 3.29 |
| `text_placeholder` | `#6A6A6A` | 5.41 | 4.92 | 4.50 |

Dark's `#6E6E6E` / `#8A8A8A` already clear all three planes (3.07 and 4.54 at worst) and do
not move. `#808080` was chosen over the minimum-passing `#868686` because `#868686` is
byte-identical to light `border` — harmless but a guaranteed reviewer double-take.

**2. Spec §4's type tokens are excluded from 8.2.** §4 claims "no typographic scale exists
today". It does: `gui/theme_manager.py` defines `TYPE_SCALE` with roles
`caption/body/label/heading/display` in **points** (9/10/12/14/17), enforced by
`tests/test_type_scale.py`, one of whose tests asserts `font_css("subheading")` raises
`KeyError` — and `subheading` is one of §4's proposed role names. Adding `font_size_*` in
px would install a second scale in a different unit with an overlapping-but-different role
set: exactly the duplication `shared/` exists to prevent. Type is deferred to 8.5, which is
where a component library actually needs type roles and can unify the two properly. This
narrows 8.2; it adds nothing. See the open question at the end of this plan.

```python
def _relative_luminance(hex_color: str) -> float:
    """WCAG 2.1 relative luminance of an #RRGGBB color."""
    raw = hex_color.lstrip("#")
    channels = [int(raw[i:i + 2], 16) / 255 for i in (0, 2, 4)]
    linear = [
        c / 12.92 if c <= 0.03928 else ((c + 0.055) / 1.055) ** 2.4
        for c in channels
    ]
    return 0.2126 * linear[0] + 0.7152 * linear[1] + 0.0722 * linear[2]


def contrast_ratio(fg: str, bg: str) -> float:
    """WCAG 2.1 contrast ratio between two #RRGGBB colors, 1.0 to 21.0.

    Symmetric in its arguments -- the names are for the caller's benefit.
    """
    lighter, darker = sorted(
        (_relative_luminance(fg), _relative_luminance(bg)), reverse=True
    )
    return (lighter + 0.05) / (darker + 0.05)
```

### Task 3: Enforce the contrast matrix in `validate_theme`

```python
def validate_theme(theme: ThemeTokens) -> None:
    """Raise ValueError if a theme violates the 8.1 design-system contract.

    green throughout.
```

## Open question for the user — does not block Stage B

**Should the type scale move into `shared/theme.py`, and when?**

Spec §4 proposes `font_size_display/heading/subheading/body/caption` as px tokens on
`ThemeTokens`. But `gui/theme_manager.py` already defines `TYPE_SCALE` with roles
`caption/body/label/heading/display` in **points** (9/10/12/14/17), and
`tests/test_type_scale.py` both forbids any hardcoded `font-size:` elsewhere in `gui/` and
asserts that `font_css("subheading")` raises — `subheading` being one of the spec's own
proposed names. The spec's claim that no scale exists is the third instance of that document
being written from field lists rather than measurements.

This plan defers type entirely. Three ways forward, for whenever it is convenient to answer:

1. **Defer to 8.5** *(what this plan assumes)*. The component library is the first thing
   that genuinely needs type roles across both apps, and it can unify the two scales in one
   move instead of leaving them coexisting.
2. **Port `TYPE_SCALE` into `shared/theme.py` now**, in points, keeping the existing role
   names, and have `gui/theme_manager.py` re-export it. Bigger diff, touches the guard test,
   but packing-tool gets a type scale it currently lacks.
3. **Add §4's px tokens as specified** and reconcile later. Not recommended: two scales in
   two units with overlapping role names is exactly the duplication `shared/` exists to
   prevent.

Answering 1 vs 2 changes 8.5's shape, not 8.2's. Stage B proceeds under option 1.
