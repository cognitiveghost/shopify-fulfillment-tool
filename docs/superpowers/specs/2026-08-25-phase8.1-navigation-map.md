# Phase 8.1 — Navigation map (before / after)

**Status:** awaiting user sign-off. Deliverable 2 of 2; companion to
`2026-08-25-phase8.1-design-system-design.md`.

The scope doc records navigation rework as chosen **against the recommendation, with the
retraining risk flagged and accepted**, and requires that this map be signed off before any
navigation code is written. Nothing here is implemented until that happens; 8.6 is the item
that would build it.

This document is cheap to change. If the structure below is wrong, say so and it gets
rewritten — no code depends on it yet.

menu bar:  File · Session · …          toolbar: (duplicates several menu actions)

## 2. The diagnosis

**Analysis Results already has two entry points, and neither is "click the tab".**

1. Session Setup runs an analysis and lands the user on Results.
2. Session Browser double-click → `on_session_selected` → `load_existing_session`, which
   ends with `self.main_tabs.setCurrentIndex(1)` under the comment *"Auto-switch to
   Analysis Results tab (Tab 2)"* (`gui/main_window_pyside.py`). Opening a past session
   jumps straight to Results, skipping Setup entirely.

Both paths converge on the same view, and both arrive by code, not by the user clicking the
tab. Results is therefore **not step 2 of a wizard** — it is *the view of whichever session
is currently open*, and how that session got opened is incidental to it.

**What the tab strip actually gets wrong** is narrower than "it shows a sequence as peers":
it offers a third way in that neither real path uses — clicking Results with no session open
at all — and that is the only case that renders blank. The strip advertises a destination
that is only ever reached as a consequence of something else.

**The two apps share staff but share no model.** The same people use both back-to-back in a
shift. One is a tab strip, the other is an invisible stack plus a menu bar plus a toolbar.
Nothing learned in one transfers to the other.

**Two secondary problems.** "Information" names nothing — it holds statistics and two logs.
"Tools" is a grab-bag of two unrelated generators.

## 3. After

One shell in both apps: **a left rail of destinations, with each destination owning its own
views.**

The rail is not a new invention for this codebase. `SETTINGS_NAV_GROUPS` is the same
pattern, it already replaced a horizontal strip that had outgrown itself, and it has been
through user contact. Reusing a proven in-repo pattern is most of why this shape was chosen.

### Shopify Tool

```
┌────────────┬───────────────────────────────────────────────┐
│ ▸ Session  │  Session — 2026-08-25 morning                 │
│   History  │  [ Setup ] [ Results ]     loaded from History │
│   Activity │  ┌─────────────────────────────────────────┐  │
│   Tools    │  │  current view                           │  │
│            │  └─────────────────────────────────────────┘  │
├────────────┤                                               │
│   Settings │                                               │
└────────────┴───────────────────────────────────────────────┘
```

| rail entry | was | contains |
|---|---|---|
| **Session** | Session Setup + Analysis Results | the currently open session; Setup and Results are its two views |
| **History** | Session Browser | unchanged — opening a session from here switches to Session/Results, as it already does |
| **Activity** | Information | Statistics · Activity Log · Execution Log |
| **Tools** | Tools | Reference Labels · Barcode Generator |
| **Settings** | (separate window) | unchanged — see §4 |

**Session** is one destination holding one session, named in the header so it is never
ambiguous which one is loaded. `StepHeader` reports how the session got there — built via
Setup, or loaded from History — rather than implying a wizard the user must walk. Results is
reachable directly whenever a session is open, because that is already true today.

With no session open at all, **Session** shows an `EmptyState` pointing at Setup and History
as the two ways to get one. That replaces the blank table, which is the single concrete
defect this section exists to fix.

### Packing Tool

```
┌─────────────┬──────────────────────────────────────────────┐
│ ▸ Pack      │  Pack                                        │
│   Statistics│  ● Select session ──── ○ Packing              │
│             │  ┌────────────────────────────────────────┐  │
├─────────────┤  │  Order Items | Session Summary         │  │
│   Settings  │  └────────────────────────────────────────┘  │
└─────────────┴──────────────────────────────────────────────┘
```

The `QStackedWidget` swap becomes the step advance inside **Pack** — which is what it
already is semantically; it just gains a visible indicator instead of being invisible. The
inner `Order Items | Session Summary` tabs stay: those two genuinely are peers.

Packing keeps a real step indicator where Shopify's Session does not, and the asymmetry is
deliberate: you cannot pack a session you have not selected, so that *is* a hard sequence.
Shopify's Setup and Results are not — either can be the first thing you see.

**Statistics** is promoted out of the session screen's tab pair to a rail destination,
matching Shopify Tool's Activity.

**The menu bar shrinks to File and Help.** Everything reachable from the rail is removed from
the menus, so each destination has exactly one path rather than two or three. The toolbar
keeps only actions that operate on the *current* screen.

## 4. Decisions and their reasons

**Settings stays a separate window in both apps.** Folding it into the rail would nest a
left-nav inside a left-nav, and settings has Save/Cancel semantics the rail does not. Only
its entry point moves, into the rail footer, so it is found the same way in both apps.

**"Information" → "Activity".** It holds statistics and two logs; all three are records of
what happened.

**"Tools" keeps its name.** It is a grab-bag, but it is a *small, honest* grab-bag and
renaming it buys nothing.

**Peers keep tabs; only the top level changes.** The inner tab pairs that survive —
Activity's three, Tools' two, Pack's two, and Setup/Results inside Session — are genuine
peers. Tabs are the right control for peers. This map removes the *top-level* strip, where
five items of two different kinds were flattened into one row; it does not push tabs out of
the places they were already correct.

---

## 5. Retraining — the accepted risk

The scope doc requires 8.6 to split navigation from cosmetic restyle into separate commits
so navigation can be reverted independently. This map adds one ordering constraint:

**Structure and labels do not change in the same release.** The first release moves the tabs
into the rail keeping every label verbatim — `Session Setup`, `Analysis Results`,
`Session Browser`, `Information`, `Tools`. The renames in §3 land a release later. Staff
learn one change at a time, and if the rail itself is rejected, it is reverted without a
vocabulary change tangled into the diff.

This costs one extra commit and is the cheapest available insurance on a risk the user has
already accepted.

## 6. Resolved: the Setup → Results question

An earlier draft asked whether Setup → Results is a sequence staff walk in order, or whether
they re-open Results on its own for an earlier session. **The code answers it: both, and the
second is already implemented.** `load_existing_session` switches to Results directly
(`gui/main_window_pyside.py`), so re-opening Results alone is a first-class, shipped path,
not a hypothetical.

That is why §3 does not move Results into History, which is what the either/or framing
implied. Results belongs to *the open session*; History is one of the two ways a session
becomes open. The design accommodates both entry points because the app already does.

Two alternatives remain recorded so the choice can be re-litigated cheaply:

- **Keep the tab strip, fix only the defects.** Lowest risk, zero retraining — but it leaves
  a top-level tab that is only ever reached as a side effect, and whose cold state is the
  blank screen. A legitimate answer if the retraining cost is judged too high.
- **Rail in Shopify Tool only.** Halves the retraining, but abandons the shared model, which
  was the main argument for touching packing-tool's navigation at all.

**What still needs the user, and does not block:** how *often* staff open a past session from
History versus building a new one. The code proves the path exists; it cannot say whether it
is daily or rare. That only affects which view **Session** opens on by default — a one-line
decision that can be made during 8.6 with real usage in hand.
