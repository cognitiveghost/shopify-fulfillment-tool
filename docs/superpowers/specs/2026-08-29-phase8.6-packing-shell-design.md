## 1. Why this half exists

8.6's brief says NavRail and CommandBar are "wired into **both** apps' main windows". The
shopify half shipped. The packing-tool half was never started — `grep -l "NavRail\|CommandBar"`
over packing-tool's `origin/main` returns nothing — which is why the subtask stayed unticked
through four merged Phase 8 PRs.

The brief also oversells the symmetry. The parent spec's §5 migration table is the actual
contract, and it scopes the two components differently:

| line | component | earned by |
|---|---|---|
| §5:306 | **NavRail** | "every Depot screen; **the tab bar; Parcker §09 app chrome**" |
| §5:307 | **CommandBar** | "every Depot screen" |

So NavRail is contracted for both apps. **CommandBar is contracted for shopify only.** This
design ships a rail in packing-tool and does *not* port CommandBar — see §8.

## 2. The root cause, and why this is smaller than it looks

`gui/icons.py` exists in both repos. The two files are byte-identical except **two lines**:

| line | packing-tool | shopify |
|---|---|---|
| 17 | `from gui.theme import current_tokens` | `from .theme_manager import get_theme_manager` |
| 74 | `color = current_tokens().text` | `color = get_theme_manager().get_current_theme().text` |

NavRail is unportable for the same single reason. It needs three things from a theme module
and packing-tool provides none of them under those names:

1. **Tokens** — shopify `get_theme_manager().get_current_theme()`, packing `current_tokens()`.
2. **`font_css`** — lives in shopify `gui/theme_manager.py:332`. Not in `shared/` at all.
3. **A `theme_changed` signal** — NavRail's `_apply_theme` connects to one so a widget-level
   stylesheet does not outrank the app's after a toggle. packing-tool's `gui/theme.py` has
   **no signal**; its own `ponytail:` comment defers that to 8.9.

This is one missing shared fact, not three problems. Fix it once in `shared/` and both
`icons.py` and `navrail.py` become portable with no further edits.

**Do not solve this by copying `navrail.py` into packing-tool.** Two copies drift, and
`shared/` is authored in packing-tool anyway — so the promotion direction is
packing-tool → `scripts/sync_shared.py` → shopify, with shopify's copies deleted in the same
cycle.

## 3. `shared/theme.py` grows the theme fact

`shared/theme.py` already imports QtWidgets (it builds stylesheets and palettes, and
`shared/server_connection.py` ships a dialog), so a `QObject` here crosses no new boundary.

Add:

- **`theme_notifier`** — a module-level `QObject` with a `changed` signal.
- **`current_tokens()`** — the tokens for the theme currently applied.
- **`set_current(name)`** — the single write path; emits `theme_notifier.changed`.
- **`TYPE_SCALE`, `TypeStyle`, `type_style()`, `font_css()`** — moved down verbatim from
  shopify `gui/theme_manager.py:211-341`, together with the density profile they read.

Each app keeps its own `apply_theme` mechanics — the QSettings org differs (`"PackingTool"`
vs shopify's) and packing-tool layers the bundled font family on via `gui/fonts.py`. They
simply call `set_current(name)` at the end of their existing apply path.

Both apps' theme modules already advertise themselves as "a thin wrapper over shared.theme".
This makes that true.

> `ponytail:` shopify's `ThemeManager.theme_changed` stays as-is for its 10 existing call
> sites rather than being rewritten to the shared notifier. Both fire from the same apply
> path, so they cannot desync. Collapse them when a second shared component needs the signal.

## 4. Rail width — the one place the 56px constant does not survive

The parent spec specifies NavRail at **56 px**. That number was authored from Depot, the
desk-density design. It does not fit packing-tool, and this was measured, not assumed.

`tests/test_navrail_labels_fit.py` (shipped by #303) defines the budget as
`RAIL_WIDTH - 8` less 5% headroom, measured in DejaVu Sans as a pinned Linux proxy. At
56 px that is **45.6 px**. Measured advances for packing-tool's labels:

| label | 9 pt (desk) | 10 pt (floor) |
|---|---|---|
| `Packing` | 46 px ✗ | 50 px ✗ |
| `Statistics` | 55 px ✗ | 59 px ✗ |
| `Session Browser` | 98 px ✗ | 106 px ✗ |
| `Browse` | 44 px ✓ | 47 px ✗ |

**Every existing label elides at 56 px, at both densities.** Even "Packing" — by 0.4 px at
desk density, which is inside the noise of the proxy font, but it fails the gate as written.

Shopify's answer in #303 was to abbreviate all five labels (`Setup`, `Results`, `Browse`,
`Info`, `Tools`). packing-tool cannot copy that: it has only two existing destinations and
abbreviating both would be a rename, which guardrail 2 forbids in the same release as the
move (§9).

**Resolution: `RAIL_WIDTH` becomes a constructor argument, default 56.** Shopify passes
nothing and is unchanged. packing-tool passes **76**, giving a budget of `(76-8)×0.95 =
64.6 px`, which clears `Statistics` at 59 px with 9% margin — so the rail also survives 8.9
moving packing-tool to floor density without a second widening.

72 px was considered and rejected: its 60.8 px budget leaves `Statistics` only 1.8 px of
margin at floor density, which the proxy font cannot honestly guarantee.

## 5. Destinations and labels

Three destinations, in this order:

| # | page | rail label | tooltip |
|---|---|---|---|
| 0 | Packing | `Packing` | `Packing — the current session's orders` |
| 1 | Statistics | `Statistics` | `Statistics — session totals` |
| 2 | Session Browser | `Browse` | `Session Browser — active, completed and available sessions` |

`Packing` and `Statistics` ship **verbatim** — that is what the 76 px rail buys, and it is
what keeps guardrail 2 intact.

`Browse` is not a rename. Session Browser has never had a rail or tab label to change: today
it is a *dialog title* (`main_window.py:2368`). A new destination is free to be named, and
the full name is in the tooltip.

**Packer Mode is not a destination.** It stays what it is — a full-screen modal state on the
outer `stacked_widget`, entered from the primary action and exited back. It takes over the
whole window, rail included.

## 6. Keep the QTabWidget; hide its tab bar

Mirror what shopify's `gui/ui_manager.py:203-207` did, for the reason stated there: swapping
the class rewrites every call site and every shortcut to produce a screen no user can tell
apart.

So `gui/main_window.py:244`'s `self.session_tabs = QTabWidget()` stays. It gains
`tabBar().hide()` and a **third tab** holding the Session Browser. The rail drives
`setCurrentIndex`, and the tabs' `currentChanged` drives the rail back — the back edge is
load-bearing, because code that jumps pages directly must not leave the rail lit on the page
the user left.

`SessionBrowserWidget` (`gui/session_browser/session_browser_widget.py:44`) is **already a
plain `QWidget`**. `open_session_browser` (`main_window.py:2362`) only wraps it in a
throwaway non-modal `QDialog`. Promoting it to a page deletes the wrapper; the widget itself
is untouched. Its `resume_session_requested` and `start_packing_requested` signals
(`:55-56`) keep their names and payloads.

The search field (`main_window.py:240`) moves onto the Packing page. It filters the order
tree via `_filter_orders`; with three destinations a window-level search field would claim
to filter pages it does not touch.

## 7. Deleting the Shopify Session entry point

Per the user's instruction of 2026-08-29: *"Shopify session button should be deleted, all
sessions will go through session browser."*

This was verified rather than assumed. For the per-packing-list mode — the way the dialog was
actually used — the browser covers it:

- `gui/session_browser/sessions_list_widget.py:4` — "Shows all sessions (**started +
  available packing lists**) for the currently selected client."
- It is keyed per packing list (`packing_list_name`, `:451`/`:540`/`:646`), the same
  granularity `SessionSelectorDialog` offered.
- `refresh_available_lists()` (`:107-108`) performs the same scan for lists not yet in the
  registry.

**One capability is dropped, and this is not a lossless refactor.**
`SessionSelectorDialog` offered *two* modes (`main_window.py:2106-2109`): "select specific
packing list **or load entire session**". The second loaded a whole multi-list session at once
from `analysis_data.json` into a `full_session/` work dir. The browser has no equivalent, and
this design does not add one — the user's instruction was that all sessions go through the
browser, and the browser is per-list.

`PackerLogic.load_from_shopify_analysis` is not deleted: it survives on the crash-recovery path
through `MainWindow.start_session`. So restoring the mode later is a UI question, not a
re-implementation. **Confirm before merge that nobody loads a whole session in one go.**

Removed:

- The `Shopify Session` toolbar button (`main_window.py:356-360`).
- The `Open Shopify Session...` menu action and its `Ctrl+O` shortcut (`:307-311`).
- `open_shopify_session()` (`:2101`).
- `gui/session_selector.py` — **777 lines**, whose only non-test caller is that method.

**Net, this item deletes more code than it adds.**

### The one test that must survive the dialog

`tests/test_session_selector_packing_lists.py` exists to prove the selector sees a packing
list uploaded *after* the registry was built. Its own docstring notes the browser does the
same thing via `RegistryRefreshWorker` — so the test was already documenting a parity it did
not assert.

That behaviour still matters. **Repoint the test at `SessionBrowserWidget`; do not delete it
with the dialog.** `tests/test_screen_primaries.py:30-31` also constructs the dialog to check
its one primary button — that case dies with the screen and is removed.

## 8. Chrome, and why CommandBar is not ported

packing-tool's menubar and toolbar carry the same actions twice today: `Session` menu holds
Open Shopify Session / Session Browser / End Session, and the toolbar holds the same three
plus Start Packing and SKU Mapping — the latter also under `Settings`.

8.6 resolves only the duplication the rail itself creates:

- `Session Browser` leaves both the menu and the toolbar — it is a destination now.
- `Open Shopify Session` leaves both — deleted outright (§7).
- What remains in the toolbar is the session's own state and actions: the client selector,
  the session info label, `Start Packing` (the one primary), `SKU Mapping`, `End Session`.

**CommandBar is not ported.** It is not shareable as written — its signals are
`clientChanged` / `clientMenuRequested` / `createClientRequested` / `manageGroupsRequested` /
`refreshRequested`, and `set_clients_from(data: dict)` reads shopify's client-*group* data
shape. packing-tool's `client_combo` (`main_window.py:230`) is a flat list from
`load_available_clients()`. Generalising across those two models would be speculative, and
the parent spec's §5 sets the rule: *a component exists when two screens need it.*

Consequence worth stating plainly: because Session Browser is now both a destination and the
only way in, the client selector must stay reachable from every page. It stays in the top
bar — it does not move onto the browser page.

## 9. Guardrails, and how this design satisfies them

Both are carried forward from the parent spec §6. The user accepted navigation-change risk
deliberately; warehouse staff use both apps daily, so nav changes mean retraining.

1. **Navigation rework lands in separate commits from cosmetic restyle.** See §11.
2. **Structure and labels do not change in the same release.** Satisfied exactly: the two
   existing destinations keep their labels verbatim (which is what §4's 76 px rail is for),
   and the only new label names a destination that never had one.

**Density is not changed here.** packing-tool has no density call anywhere (`main.py` applies
a theme and nothing else) and no type scale — it uses raw `setPointSize()`. Parcker puts it at
floor density, but switching it re-sizes every screen, so that belongs to 8.9, which already
owns Packer Mode's `display_xl`. 8.6 ships packing-tool at the desk default. §4's rail width
is chosen so that 8.9's switch needs no rework here.

## 10. Acceptance tests

1. `shared.theme.set_current()` emits `theme_notifier.changed` exactly once per change, and
   not at all when the theme is re-applied unchanged.
2. `font_css("caption")` returns the same string from both repos after `sync_shared.py`.
3. Every packing-tool rail label fits its rail at both 9 pt and 10 pt — the #303 test,
   parameterised by the app's own `RAIL_WIDTH` instead of the module constant.
4. The rail and the hidden `QTabWidget` stay in sync in **both** directions, including when
   a page is changed programmatically rather than by a rail click.
5. Selecting `Browse` shows the same `SessionBrowserWidget` instance the dialog used to
   host, and `start_packing_requested` still reaches `main_window`.
6. A packing list uploaded after the registry was built is visible in the browser — the
   repointed `test_session_selector_packing_lists.py` (§7).
7. `grep -r "SessionSelectorDialog"` returns nothing outside git history.
8. The theme toggle repaints the rail: after toggling, the rail's stylesheet reports the new
   `surface_sunken`. This is the regression the missing signal would have caused.
9. `tests/test_style_literals_guard.py` still passes — its `SCOPE` already covers `shared/`,
   so `shared/navrail.py` and `shared/icons.py` are policed automatically on arrival.

Gate for both repos: `ruff check .` and `python -m pytest`
(`QT_QPA_PLATFORM=offscreen` on the shopify side).
