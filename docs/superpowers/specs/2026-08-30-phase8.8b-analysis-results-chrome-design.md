# Analysis Results 1b — the chrome (Phase 8.8b)

Second and last cycle of Analysis Results 1b. 8.8a changed the table's **unit**
(one row per order) and left the screen looking exactly as it did. This cycle
changes how it **looks**, and changes nothing about what it operates on.

Parent spec: `2026-08-30-analysis-results-1b-design.md` §8 and §9. That document
decided *what* moves; this one decides *where each piece lands in this repo* and
*what gets deleted*.

Everything here is presentation. No file under `shopify_tool/` is touched, and
`analysis_results_df` remains the single source of truth for every action,
report, export and undo step.

---

## 1. The four items, and one regression 8.8a left behind

Spec §8 lists four: KPI strip, status edge, `ContextualSelectionBar`,
`FilterBar`. Reading the shipped code found a fifth thing that belongs in this
cycle because it is the same surface:

**The repeat-order highlight is dead on `main` right now.** `PandasModel`'s row
tint keys off `System_note`, and `System_note` is line-level — `orders_frame`
does not carry it. So since #307 merged, an order whose note says
`"Repeat customer…"` paints like any other. Nothing failed; the branch is simply
never taken. `orders_frame` extracts `Blocker` out of `System_note` and drops the
rest.

The status edge is the surface that shows this signal, so restoring it is part of
building the edge, not a separate errand (§4).

## 3. The filter row

Session Browser 1e settled the pattern and this screen follows it verbatim:
`FilterBar` owns the **search field and the result count**; every other filter
control sits beside it in the same `QHBoxLayout`, not inside it.

- `filter_input` becomes an alias for `filter_bar.search_field`. Keeping the
  attribute name means `apply_filter()`, its signal wiring and
  `test_analysis_results_1b.py` are untouched by this cycle.
- `clear_filter_button` is deleted. `QLineEdit.setClearButtonEnabled(True)` is
  already on and does the same job in the field itself.
- The `"Filter by:"` and `"Tag:"` labels go. The combos keep their tooltips —
  again 1e's choice.
- `case_sensitive_checkbox`, `filter_column_selector` and `tag_filter_combo`
  survive unchanged. They are warehouse-facing controls and this is a restyle.

**No filter chips.** `FilterBar` supports them, and 1e's own comment says why not
to use them here: the scope combo and the tag combo already draw their state, and
a chip would draw it a second time. Chips earn their place when a filter has no
other visible representation.

`filter_bar.set_count()` shows `"312 orders"`, or `"48 of 312 orders"` while a
filter is active — the count moves off the footer and next to the thing that
changes it.

### The `⋯` overflow

Spec §8: *screen-level buttons that are not per-selection go to the command bar
or the row's overflow — one primary action per screen*.

`generate_reports_button_tab2` is already this screen's declared primary
(`_SCREEN_ACTIONS[1]`, PR #305): it stays a hidden `QPushButton` bound into the
`CommandBar`, exactly as today.

The other five become `QAction`s in a `QToolButton` menu at the right end of the
filter row: **Add Product to Order, Configure Columns, Settings, Undo, and the
theme toggle.**

This conversion is free. Every existing call site touches these objects through
`setEnabled`, `setToolTip` or `setText` only — all three are `QAction` methods
with identical signatures — so `main_window_pyside.py:662-701`,
`actions_handler._update_undo_button()` and `_update_theme_button_text()` keep
their code and their attribute names. `_create_results_actions()` is deleted
outright.

Undo keeps `Ctrl+Z`, which is how it is actually invoked and which the tooltip
has always advertised.

## 4. Status as an edge

### The model stops carrying colour

`PandasModel` currently answers `BackgroundRole` and `ForegroundRole` from two
per-row caches of `QColor`. Both roles and both caches go, along with the
`self.colors` / `self.text_colors` maps.

In their place, one cache of **theme role token names**, exposed on a new item
role:

```python
ROLE_STATUS = Qt.ItemDataRole.UserRole + 20   # str token name, or None
```

`_build_row_color_cache()` becomes `_build_row_status_cache()` and returns
`"status_warning"` / `"status_success"` / `"status_danger"` / `None` instead of
colour pairs. The classification is unchanged, so no row changes meaning:

| condition | token |
|---|---|
| the order repeats (§4, below) | `status_warning` |
| `Order_Fulfillment_Status == "Fulfillable"` | `status_success` |
| `Order_Fulfillment_Status == "Not Fulfillable"` | `status_danger` |
| otherwise | `None` |

Repeat wins over blocked. That is what the row tint did — the `"Repeat"` branch
`continue`d before the status branch was reached — so a blocked repeat order has
always shown amber, not red. Preserved deliberately, not chosen fresh.

Caching token *names* rather than colours makes the cache theme-independent, so
`_update_colors()` collapses into a repaint: a theme change no longer rebuilds
anything, it just re-emits `dataChanged`. The delegate resolves the token against
the live theme at paint time.

### The delegate

New `gui/status_edge_delegate.py`, one class, modelled on
`SessionStatusDelegate`: a pure method holds the rule so it is testable without a
painter, and `paint()` draws the base item first so the stylesheet's selection
ring (`shared/theme.py:912` — `selection_bg` plus a 2px `selection_border` top
and bottom) still renders underneath.

```python
def edge_token(self, index) -> str | None: ...   # pure; tested directly
```

A 3px bar in the token's colour, full row height, painted at the **left edge of
the leftmost visible column** — `header.visualIndex(index.column()) == 0`, not
logical column 0, so a user who reorders columns still gets the edge on the left.

Installed with `setItemDelegate()` on the results table and on the detail pane's
lines table. `setItemDelegateForColumn()` wins over it, so `TagDelegate` keeps
the `Internal_Tags` column and simply never paints an edge there. `Order_Number`
is already pinned to position 0 by the header-move guard, so the two never
collide.

The lines table gets the same treatment for free: `order_lines()` carries
`System_note`, so a repeat line shows an amber edge and every other line shows
none. Its rows lose their tint in the same commit as the order rows — a tinted
lines table beside an un-tinted order table would read as two different
languages.

### Restoring the repeat signal

`orders_view` gains a second hidden derived column beside `_search_text`:

```python
REPEAT_COLUMN = "_repeat"                       # bool
HIDDEN_COLUMNS = (SEARCH_COLUMN, REPEAT_COLUMN)
```

`orders_frame()` sets it True when any line of the order carries a `System_note`
matching the tint's existing test — `"Repeat" in note and not
note.startswith("Cannot fulfill")`. The rule is lifted verbatim from
`_build_row_color_cache()`; this cycle relocates it, it does not restate it.

`_build_row_status_cache()` reads `_repeat` when the frame has it and falls back
to scanning `System_note` when it does not, which is what makes one builder serve
both the order table and the lines table.

`update_results_table()` currently hides `SEARCH_COLUMN` by name in two places
(before and after `apply_config_to_view`, which re-walks the frame). Both become
a loop over `HIDDEN_COLUMNS`.

## 5. The KPI strip

Four `StatCard`s, in spec §8's order: **Orders, Fulfillable, Blocked, Items.**

`update_summary_bar()` becomes `update_kpi_strip()` — one call site
(`main_window_pyside.py:1160`) — for the same reason
`_update_bulk_toolbar_state()` is renamed in §6: there is no summary bar left for
it to name. It keeps computing from `analysis_results_df`; `Quantity` is
line-level, so the item count has to come from the line frame.
Three of its four numbers already exist in that method; `Blocked` is
`total_orders - fulfillable_orders`, and `fulfillable_items` stops being
computed.

With no session loaded every card reads `—`. Not `0`: an empty warehouse day and
an unloaded screen are different facts, and the old label distinguished them
("No analysis data").

## 6. The selection bar

`BulkOperationsToolbar` and its bespoke `FlowLayout` are deleted — the file goes
if nothing else imports `FlowLayout`. `ContextualSelectionBar.add_action()`
takes the label, the slot and a button role, so the nine signal declarations and
the matching nine-connection block in `main_window_pyside.py:382-403` disappear
with it; the handlers on `actions_handler` are called directly.

The bar carries, left to right: the count sentence, then **Set Fulfillable, Set
Not Fulfillable, Add Tag, Remove Tag, Delete ▾, Export ▾, Clear.** Delete keeps
its menu (Remove SKU from Orders / Remove Orders with SKU / Delete Selected
Orders) and takes the `danger` button role instead of the hand-written red
stylesheet. Export becomes a menu rather than two buttons, since XLSX and CSV are
one decision.

**`Select All` is dropped, not moved.** It is unreachable today — the toolbar
only becomes visible once something is selected, so the button that selects
everything can only be clicked when it is no longer needed. `Ctrl+A` on the table
has always done the job, and since 8.8a made rows orders it does it exactly.

`_update_bulk_toolbar_state()` is renamed `_update_selection_bar_state()` across
its five call sites. The old name would describe a widget that no longer exists.

The count sentence is formatted by the caller, per the bar's docstring:
`"3 orders · 11 items selected"`.

## 7. Two components stop going stale on a theme change

`FilterBar` and `ContextualSelectionBar` read theme tokens once in `__init__` and
never again. Toggle the theme and both keep their old surface colour. It is
invisible on `main` only because nothing on the Session Browser screen toggles
the theme — and this cycle puts the theme toggle in this screen's overflow, two
rows above a `FilterBar`.

Both get the three lines `CommandBar` already has: the stylesheet moves into
`_apply_theme()`, called from `__init__` and connected to
`get_theme_manager().theme_changed`. Fixed in the component, so the Session
Browser is fixed by the same change rather than by a second one later.

`Card` needs nothing: it sets fonts only, and takes its colours from the
application stylesheet's `QFrame` rules.

## 10. Risks

**The row tint is the biggest visual change in Phase 8 so far.** A screen that
painted whole rows green and red now paints a 3px stripe. That is the point —
Parcker's rule is that status is an edge, a chip or a tint, never a filled row,
and a filled row cannot show *selected* and *blocked* at once — but it is a real
change for staff who scan this table all day, and it lands in the same release as
five buttons moving into a `⋯` menu. Both belong in the release note. 8.8a's own
note (saved column configs appear to lose columns; the line-level ones are in the
pane) is still unshipped and should go out with them.

**`ROLE_STATUS` must not collide.** `Qt.UserRole` is unused on `PandasModel`
today, but `TagDelegate` shares the table. The number is checked against every
delegate on either table before it is written, and a test asserts the two
delegates read different roles.

**The theme fix reaches the Session Browser.** §7 changes two shared components,
so 1e's screen repaints on a theme toggle for the first time. That is the fix
working, but it is a second screen's regression surface inside a one-screen
cycle, and Stage C should look at 1e as well as at this tab.

## 11. Light theme

Unchanged from parent spec §12: dark is designed, light is derived. Every token
used here is validated on all four planes and on `selection_bg`, so contrast is
safe in both — but the light rendering is an implementer's reading until light
gets its own design pass, and the PR says so rather than claiming parity.
