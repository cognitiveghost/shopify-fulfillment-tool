# Phase 8.6 — Shell: NavRail + CommandBar

**Status:** design, Stage A. Revised after the user's Stage A review (2026-08-27).
**Parent contract:** `docs/superpowers/specs/2026-08-26-phase8-unified-design-system.md` §5, §6.
**Depends on:** 8.5 (PR #300 / packing #165, both merged @ `f892ceb`).
**Worktree:** `worktree-phase8-shell`.

---

## 1. What this item does

`NavRail` and `CommandBar` shipped in 8.5 with no call site. 8.6 gives them one: the
Shopify Tool's main window loses its tab bar, its two-row global header **and its 70 px
client-card sidebar**, and gains a 56 px rail on the left and a one-row command bar on top.

Roadmap §2 says "both apps". **This cycle covers the Shopify Tool only.** §6 below states
why the Packing Tool is a separate item.

## 2. What is on `main` today

`gui/ui_manager.py::create_widgets()` builds a horizontal layout of two things:

- `ClientSidebar` (`gui/client_sidebar.py`, 30 KB) — 70 px client cards in Pinned / group /
  All sections, an async refresh, and a context menu carrying pin, edit, move-to-group and
  delete, plus the create-client and manage-groups dialogs.
- a right-hand column of `_create_global_header()` (two rows: sidebar toggle, client
  label, connection gear / folder icon, "Session:", session label, and an `HLine`) above
  `main_tabs`, a five-tab `QTabWidget`.

`main_tabs` has 30 references across `gui/ui_manager.py`, `gui/actions_handler.py`,
`gui/main_window_pyside.py` and `tests/test_session_setup_layout.py`. `client_sidebar`
has 13.

## 3. The decisions

### 3.1 The tab widget stays as the page store; the tab bar goes

`NavRail` drives the existing `QTabWidget` through `setCurrentIndex`, and
`main_tabs.tabBar().hide()` removes the tabs from view.

The user's call: the tab widget may stay **as backend**, provided what ships looks like the
mockup. It does — nothing of `QTabWidget` remains visible once its bar is hidden. A
`QTabWidget` with a hidden tab bar *is* a `QStackedWidget` with an API this codebase already
speaks; swapping in a real `QStackedWidget` would rewrite 30 call sites, the five `Ctrl+N`
shortcuts and a test file to produce a pixel-identical screen.

**The binding is two-way, and that is load-bearing.** `actions_handler.py:256` and
`main_window_pyside.py:1157` jump the user to Analysis Results after a run. With only the
forward edge (`rail.currentChanged → tabs.setCurrentIndex`) those jumps would move the page
and leave the rail highlighting the wrong destination. So:

- `rail.currentChanged` → `main_tabs.setCurrentIndex`
- `main_tabs.currentChanged` → `rail.set_current`

The cycle terminates because both sides already early-return on an unchanged index:
`NavRail.set_current` returns before emitting when `index == self._current`, and
`QTabWidget` does not re-emit `currentChanged` for the index it is already on. No guard
flag is needed, and adding one would hide a real regression if either invariant broke.

**Icons and tooltips move to the rail.** `_TAB_ICONS` keeps its five names and its
position in `tests/test_icons.py`; `_refresh_icons()` sets `rail.button(i).setIcon(...)`
instead of `main_tabs.setTabIcon(...)`. The five `setTabToolTip` calls become
`rail.button(i).setToolTip(...)` with the same text, `Ctrl+N` hint included.

**Labels are verbatim** (parent spec §6 guardrail 2): `Session Setup`, `Analysis Results`,
`Session Browser`, `Information`, `Tools`. Renames are a later release.

### 3.2 The rail has a footer, and the connection gear lives there

Server Connection is an application setting, not a screen control. It moves to the foot of
the rail, below a stretch, per the user's Stage A choice:

```
┌──────┐
│ □    │ Session Setup
│ □    │ Analysis Results
│ □    │ Session Browser
│ □    │ Information
│ □    │ Tools
│      │  (stretch)
│ ⚙    │ Server Connection
└──────┘
```

`NavRail` gains `add_footer_item(icon_name, label) -> QToolButton`. **A footer item is an
action, not a destination:** it is not checkable, not in the exclusive `QButtonGroup`, and
its index is not part of `currentChanged`'s space. Adding it to the group would let a click
on the gear un-check the current page, leaving the rail with no destination lit while the
page beneath it did not move.

### 3.3 The CommandBar replaces the global header

`_create_global_header()` is deleted. Its contents map onto the `CommandBar`:

| header widget | becomes |
|---|---|
| `current_client_label` ("No client selected") | the client dropdown (§3.4) |
| `session_folder_icon_label` + "Session:" + `session_info_label` | `CommandBar.set_session()` |
| `connection_btn` | the rail's footer item (§3.2) |
| `sidebar_toggle_btn` | deleted with the sidebar (§3.4) |
| the `HLine` separator | the bar's own `border-bottom` |

`self.mw.session_info_label` keeps its name, pointing at the bar's label, so
`update_session_info_label()` (`main_window_pyside.py:692`) needs no edit.
`current_client_label` cannot survive as a name — a `QComboBox` has no `setText` — so
`main_window_pyside.py:838` switches to setting the dropdown's current client id. That call
is already `hasattr`-guarded.

`connection_btn` keeps its attribute name on `MainWindow` even though it now lives on the
rail, because `_BUTTON_ICONS` looks its widgets up by attribute (`ui_manager.py:83-88`) and
`tests/test_icons.py` asserts on that dict.

### 3.4 The dropdown carries the structure, and the sidebar is retired

Per the user's Stage A choice, the client sidebar does not survive. Everything it did moves
into the dropdown:

```
┌─ Client ▾ ───────────┐
│ PINNED               │
│  ● CLIENT_M          │
│ RETAIL               │
│  ● CLIENT_A          │
│  ● CLIENT_B          │
│ ALL CLIENTS          │
│  ● CLIENT_Q          │
│ ──────────────────── │
│  New client…         │
│  Manage groups…      │
└──────────────────────┘
right-click a client row →
pin / edit / move to group / delete
```

**There is no client "tags" concept in this codebase** — `Tags` is an order column, and
`tag_categories_dialog.py` styles order tags. What a client actually carries is
`is_pinned`, a `custom_color` (`profile_manager.get_ui_settings`) and membership in a group
that has its own name and colour (`groups_manager.list_groups`). So the dropdown's
structure is pinned / groups / all, and the dot on each row is the client's `custom_color`.
Every one of those values is already in the dict `_gather_refresh_data()` returns, so the
richer dropdown costs **no additional file-server IO**.

**It stays a `QComboBox`.** Section captions are rows with `Qt.NoItemFlags`, the dot is a
`Qt.DecorationRole` pixmap, and the two actions at the foot sit under a separator. A
`QToolButton` + `QMenu` would draw the sections more naturally but would throw away
`set_clients` / `current_client` / `clientChanged` — the API 8.5 shipped and tested — plus
keyboard navigation and the free display of the current selection.

**Where the sidebar's logic goes.** `CommandBar` lives in `gui/components/` and owns no
application state; it must not grow a `ProfileManager`. So the sidebar's data and actions
move to a new `gui/client_directory.py`:

- `ClientDirectory(QObject)` owns `profile_manager` and `groups_manager`.
- `refresh()` — the existing async `Worker` + `_gather_refresh_data()` verbatim, including
  the strong-reference set that keeps in-flight workers alive.
- `loaded = Signal(dict)` — the full refresh dict, so the bar can build its sections.
- `menu_for(client_id, parent) -> QMenu` — the existing `_show_context_menu` body.
- `open_groups_dialog()` / `open_create_client_dialog()` — moved verbatim.

The bar stays dumb: it emits `clientMenuRequested(str, QPoint)` and its owner supplies the
menu. `MainWindow` owns the directory, exactly as it owned the sidebar.

**This makes the navigation commit no longer the last one.** §5 splits accordingly.

## 4. Two tracks, one branch, one PR

The retirement is a 30 KB deletion with a new module and three dialogs re-wired. It does not
fit in one Stage B beside the rail and the bar. It is not deferred to a later item — the
user chose retirement over deferral — it is **sequenced within this item**:

- **Track 1 — the shell.** Rail (with footer), command bar, structured dropdown, sidebar
  present but collapsed. Complete and pushable on its own.
- **Track 2 — the retirement.** `gui/client_directory.py`, the context menu on the
  dropdown, `gui/client_sidebar.py` deleted.

If Stage B runs long after Track 1, push it and leave `next_stage: B`. Do not leave Track 1
half-applied.

## 5. Commit split

Parent spec §6 guardrail 1: navigation must be revertible on its own.

1. **Chrome.** `CommandBar` in, `_create_global_header()` out, structured dropdown, sidebar
   collapsed. No page-switching behaviour changes.
2. **Navigation.** `NavRail` in with its footer gear, tab bar hidden, the two-way binding,
   icons and tooltips moved. Reverting this one commit restores the tab bar and leaves the
   command bar standing.
3. **Retirement.** `ClientDirectory` in, `ClientSidebar` deleted. Last, so that reverting
   navigation never has to reason about a deleted file.

## 6. Why the Packing Tool is not in this cycle

Two findings from `packing-tool@origin/main`:

- **It has no tab bar to replace.** Its top level is a two-page `QStackedWidget` (session
  view ↔ packer mode) driven by a menu bar and toolbar. Packer mode is deliberately
  full-bleed at floor density. A rail there would hold two items, one of which is entered
  by scanning rather than clicking — worse than the menu bar it would replace.
- **It does have a command bar already, unnamed.** `gui/main_window.py:213-233` is a
  "Client:" label plus a `QComboBox` in a bordered row. That *is* `CommandBar`.

Giving it the real component means moving `NavRail`/`CommandBar` from shopify's
`gui/components/` into `shared/`, which needs the same treatment 8.5 gave the shared
widgets: `theme` becomes an explicit argument, and `icon()` resolution moves to the caller
because `shared/` may import neither app's `gui`. The 8.5 handoff recorded "do not
pre-move" for exactly this reason.

**Open question for the user, ahead of 8.6b:** does the Packing Tool get a NavRail at all,
or only the CommandBar? The recommendation is CommandBar only — there is nothing for a rail
to navigate — but Parcker §09 names app chrome as something the rail replaces, and the
merged spec does not resolve that against the Packing Tool's actual two-view flow.

## 7. Acceptance

A new `tests/test_shell.py` covering, headless:

1. `main_tabs.tabBar().isVisible()` is false and the rail has five destinations.
2. Rail labels equal the five tab titles verbatim — the guardrail as an executable check.
3. Clicking rail item *n* moves `main_tabs` to *n*.
4. `main_tabs.setCurrentIndex(1)` — the `actions_handler` path — moves the rail to 1.
5. `_refresh_icons()` leaves every rail button with a non-null icon after a theme toggle.
6. The footer gear is **not** checkable and clicking it leaves `current_index()` unchanged.
7. The command bar carries client, session and status, and the header widgets are gone.

A new `tests/test_client_directory.py` covering:

8. The dropdown's rows are ordered pinned → groups → all, with section captions
   unselectable and each client's `custom_color` on its row.
9. `set_clients_from(data)` twice in a row does not duplicate rows or emit `clientChanged`.
10. Choosing "Manage groups…" opens the dialog and does **not** change the current client.
11. `ClientDirectory.menu_for` offers pin/unpin against the client's real pinned state.
12. `refresh()` keeps a strong reference to its in-flight worker.

Plus the repo gate: `QT_QPA_PLATFORM=offscreen python -m pytest` and
`ruff check . --exclude shared`.
