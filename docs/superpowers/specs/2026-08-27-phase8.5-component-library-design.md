# Phase 8.5 — Component library: the six from spec §5

**Date:** 2026-08-27
**Roadmap item:** 8.5 (`docs/superpowers/plans/2026-08-26-phase8-roadmap.md`)
**Contract:** `docs/superpowers/specs/2026-08-26-phase8-unified-design-system.md` §5
**Worktree/branch:** `worktree-phase8-components` (both repos)

---

## 1. What this item is, and what it is not

Build the six components spec §5 earns, land the four-variant button hierarchy, and
change `StatusDot` to take a token name instead of a hex string.

**Nothing is wired into a screen.** 8.6 wires NavRail and CommandBar into both main
windows; 8.7 and 8.9 wire the rest. 8.5 ships widgets plus their tests, and exactly one
call-site edit — packing-tool's single `StatusDot(...)` — because that one is forced by
the API change, not chosen.

Consequence, stated plainly: at the end of 8.5 five of the six components have no call
site. That is the roadmap's sequencing, not an oversight. The alternative — build each
component inside the cycle that first needs it — was rejected when the phase was planned
because NavRail and CommandBar are needed by *both* apps simultaneously in 8.6.

## 2. What already exists (do not rebuild)

Checking `origin/main` before designing changed three of the six decisions.

### 2.1 The button hierarchy is half-built, and its hard call is already made

`gui/theme_manager.py:355-480` already carries:

- `BUTTON_ROLES = ("primary", "secondary")`
- `role_stylesheet(theme)` — attribute-selector QSS, appended after `shared.theme`'s sheet
- `set_button_role(button, role)` — with the `unpolish`/`polish` trap already handled

Two things follow.

**The property is named `role`, not `variant`.** Spec §5 writes
`setProperty("variant", ...)`. The repo shipped `role` first, with call sites and a
raising validator. Reuse beats renaming: **8.5 extends `BUTTON_ROLES`, it does not
introduce a parallel `variant` mechanism.** Spec §5's naming yields to the code.

**Opt-in stays opt-in.** `role_stylesheet`'s docstring already decided the question 8.5
would otherwise have to ask:

> Deliberately opt-in: a button with no `role` property keeps exactly its current
> appearance. The opposite arrangement (neutral by default, mark the primaries) is fewer
> edits but restyles every button in the app at once, and this is a Windows-only app with
> three tracks of visual change not yet verified on Windows.

There are **112 `QPushButton(` sites in shopify and 35 in packing-tool**. Flipping the
default in 8.5 leaves 147 buttons neutral with no screen designating a primary until 8.6
and 8.7 land — a release cut mid-phase would ship an app with no call to action anywhere.
So 8.5 adds `ghost` and `danger` to the existing opt-in mechanism and **does not flip the
global default**. The flip belongs in the cycle that touches screens and can name each
screen's primary in the same commit.

### 2.2 `STATUS_CONFIG`'s seven hexes are already gone

Spec §5 says StatusChip "replaces `STATUS_CONFIG`'s 7 hexes". 8.3 already did that.
On packing-tool `origin/main` the table maps status → **token name**:

```python
"completed": {"label": "Completed", "role": "status_success"},
```

and the call site reads `StatusDot(getattr(current_tokens(), cfg["role"]))`. So the hex
eradication is done; what remains is moving the `getattr` *inside* the widget, which is
precisely the "role name, not a hex string" change 8.5 is asked for.

Note the wrinkle this creates: `not_started` maps to `text_secondary`, which is **not**
one of the four status roles and has no `_bg` tint partner. The API must accept any
`ThemeTokens` field name, not only `status_*`. See §4.1.

### 2.3 `Card` already is the StatCard frame

`gui/components/card.py` is a framed panel holding a vertical stack of centred labels at
`TYPE_SCALE` roles. StatCard is that, with `display_xl` on the numeral and `caption` on
the sublabel. **StatCard subclasses `Card`**; it does not re-hand-roll a `QFrame`.

## 3. Placement: `shared/` vs `gui/components/`

The roadmap's Stage A question. Answer:

| component | home | why |
|---|---|---|
| `StatusDot` (changed) | `shared/theme.py` | already there; packing-tool is its only caller today, shopify's 1e needs it next |
| `StatusChip` | `shared/theme.py` | earned by 1a/1b/1c/1e **and** Packer Mode — both apps, from day one |
| button roles QSS + `set_button_role` | `shared/theme.py` | see §3.1 |
| `NavRail` | `gui/components/navrail.py` | both apps in 8.6, but shopify wires first |
| `CommandBar` | `gui/components/commandbar.py` | same |
| `StatCard` / `KpiStrip` | `gui/components/statcard.py` | 1a, 1c, Metrics tab — shopify only until 8.9 |
| `ContextualSelectionBar` | `gui/components/selectionbar.py` | 1a, 1b — shopify only |
| `FilterBar` | `gui/components/filterbar.py` | 1a, 1b, 1e — shopify only |

**Do not pre-move.** NavRail and CommandBar are wanted by both apps in 8.6, and the
temptation is to put them in `shared/` now. Resist it: `shared/` is one-way synced from
packing-tool, so a widget placed there is authored in the repo that is *not* wiring it
first. 8.6 moves them when it wires packing-tool, with the shopify implementation already
proven. A move is a `git mv` plus a sync; a premature move is a cross-repo edit loop for
every iteration of a widget still finding its shape.

`EmptyState` and `InlineMessage` stay plain labels. No component is added beyond the six.

### 3.1 Why the button QSS moves into `shared/theme.py`

`role_stylesheet` lives in shopify's `theme_manager` for a reason its own docstring
gives: "`shared/theme.py` … is sync-owned by packing-tool, so it cannot be edited here."
That constraint is about *which repo edits it*, not about where it belongs. 8.5 legitimately
edits `shared/` — from packing-tool, then `python scripts/sync_shared.py`.

Both apps need the same four button roles. Two copies of four QSS blocks is exactly the
drift Phase 8 exists to end, and packing-tool composes `build_stylesheet(tokens)` directly
(`packing-tool/gui/theme.py:59`), so moving the rules into `build_stylesheet` gives it the
hierarchy with no packing-side QSS at all.

After the move:

- `shared/theme.py` owns `BUTTON_ROLES`, the four `QPushButton[role="…"]` blocks, and
  `set_button_role`.
- shopify's `gui/theme_manager.py::role_stylesheet` keeps **only** its `QListWidget#settingsNav`
  rules, and re-exports `set_button_role` from `shared.theme` so its existing call sites
  change by zero lines.

Layer order is unaffected: attribute selectors outrank the bare `QPushButton` rule
regardless of position, and `density_stylesheet` (appended last) sets only `min-height`,
`padding` and `font-size`, none of which the role blocks touch.

## 4. The components

### 4.1 `StatusDot` — API change

```python
StatusDot(role: str, theme: ThemeTokens, diameter: int = 10)
StatusDot.set_role(role: str, theme: ThemeTokens) -> None
```

- `role` is **any `ThemeTokens` colour-field name**, not only `status_*`. `not_started`
  needs `text_secondary` (§2.2), and narrowing the type would force the one caller back
  to passing a hex for exactly one row.
- Resolution is `getattr(theme, role)`, so a typo raises `AttributeError` in development —
  the rule `font_css()` and `icons.icon()` already set in this codebase.
- **`theme` is explicit and required.** `shared/` cannot ask "which theme is live": that
  answer lives in `packing-tool/gui/theme.py::current_tokens()` and in shopify's
  `get_theme_manager()`, and `shared/` must not import either. Both callers already hold
  tokens at the call site.
- The 10 px default diameter stays. `set_color(hex)` is **removed**, not deprecated —
  there is one call site in the entire codebase and it does not use it.

Staleness across a theme toggle is unchanged from today and stays out of scope; the
`ponytail:` comment on `current_tokens()` already names it as 8.9's problem.

### 4.2 `StatusChip` — new, `shared/theme.py`

```python
StatusChip(role: str, text: str, theme: ThemeTokens, variant: str = "chip")
```

A single `QLabel` subclass with a stylesheet — no child layout, no dot widget. Two variants:

- **`chip`** — pill: `background: <role>_bg`, `color: <role>`, `border-radius`, padding.
- **`edge`** — row/lane marker: `border-left: 3px solid <role>`, transparent background,
  `color: text`.

The `chip` variant needs a tint partner. When `f"{role}_bg"` is not a `ThemeTokens` field
— which is the case for `text_secondary` — it falls back to `surface_sunken`. This is the
one place a missing token is tolerated rather than raised, because §2.2 guarantees a real
status row will always have its tint and the fallback exists for the neutral one.

`validate_theme` already proves every `status_*` against its own `_bg` at 4.5:1, so the
chip's contrast is guaranteed by the existing gate, not by a new check.

Placed beside `StatusDot` in `shared/theme.py` rather than in a new `shared/components.py`:
one more widget does not earn a module, and it keeps the sync surface at one file.

### 4.3 `NavRail` — `gui/components/navrail.py`

56 px fixed width, `surface_sunken`, no border. Vertical stack of icon-over-label buttons.

```python
rail = NavRail(parent=None)
rail.add_item(icon_name: str, label: str) -> int
rail.set_current(index: int) -> None
rail.currentChanged  # Signal(int)
```

Icons come from `gui/icons.py::icon()` (Lucide, already bundled). The rail owns selection
state and emits an index; it knows nothing about tabs, stacks or pages — 8.6 connects
`currentChanged` to whatever it replaces the tab bar with. **8.6 ships the rail with the
existing labels verbatim** (roadmap guardrail: structure never changes labels in the same
release); 8.5 does not choose labels at all.

### 4.4 `CommandBar` — `gui/components/commandbar.py`

One horizontal row: client selector (`QComboBox`), session id (`QLabel`), status
(`StatusChip`), one primary `QPushButton`.

```python
bar.set_clients(names: list[str]) / bar.current_client() -> str
bar.set_session(text: str)
bar.set_status(role: str, text: str)
bar.set_action(label: str)          # the single primary; role="primary"
bar.clientChanged   # Signal(str)
bar.actionTriggered # Signal()
```

The action button is the only `set_button_role(..., "primary")` call in the component
library — it is the screen's one primary by construction, which is how "one primary per
screen" gets enforced structurally rather than by review.

### 4.5 `StatCard` / `KpiStrip` — `gui/components/statcard.py`

```python
class StatCard(Card):
    def __init__(self, value: str, label: str, *, min_width=0, parent=None)
    def set_value(self, text: str) -> None
```

`display_xl` numeral over a `caption` sublabel, both through `Card.add_text`, both already
in `TYPE_SCALE` (`gui/theme_manager.py:196,201`). `set_value` exists because the Metrics
tab updates live; the sublabel does not change and gets no setter.

`KpiStrip` is a `QWidget` with a `QHBoxLayout` of `StatCard`s and `add(value, label)`.
It is a container, not a layout algorithm.

### 4.6 `ContextualSelectionBar` — `gui/components/selectionbar.py`

Hidden until something is selected.

```python
bar.add_action(label: str, slot, role: str = "secondary") -> QPushButton
bar.set_selection(count_text: str) -> None   # "" hides the bar
```

`set_selection("")` hides; any non-empty text shows. The caller formats the sentence
("3 orders · 11 items selected") because only the caller knows what it is counting.

This is what replaces the eleven-button row, but the replacement happens in 8.7 — 8.5
builds the bar and leaves the row alone.

### 4.7 `FilterBar` — `gui/components/filterbar.py`

Search field, a row of removable filter chips, a result count.

```python
bar.add_filter(key: str, text: str) -> None
bar.remove_filter(key: str) -> None
bar.set_count(text: str) -> None
bar.searchChanged  # Signal(str)
bar.filterRemoved  # Signal(str)   # the key
```

The chip is a private `_FilterChip` in the same module: a `QPushButton` with the label,
an `×`, and `role="ghost"`. It is deliberately **not** `StatusChip` — a filter chip is
interactive and dismissible, a status chip is a read-only badge. Sharing them would mean
one widget with a `clickable` flag, which is the abstraction this phase keeps deleting.

## 5. Cross-repo shape

Track 1 (`shared/theme.py`) is authored in **packing-tool** and pulled into shopify with
`python scripts/sync_shared.py`. Same pairing as 8.4: **two PRs, merged together.**

- **packing-tool PR** — `shared/theme.py` (StatusDot, StatusChip, button roles,
  `set_button_role`), plus its one `sessions_list_widget.py` call site, plus its own
  self-check.
- **shopify PR** — the synced `shared/theme.py`, `gui/theme_manager.py` shrunk to the
  settingsNav rules with a re-export, the five `gui/components/` widgets, and their tests.

Track 2 (`gui/components/`) is shopify-only and touches nothing in `shared/`.

**Track 1 is committable and pushable on its own.** If Stage B runs long — 8.4's was the
longest measured in the phase and this one is comparable — land Track 1 complete, push
both repos, and leave `next_stage: B`. Do not fan out to subagents, and do not leave
Track 1 half-applied across the two repos.

## 6. Testing

One file per component, matching the existing `tests/test_components_card.py` convention:
`test_components_navrail.py`, `_commandbar.py`, `_statcard.py`, `_selectionbar.py`,
`_filterbar.py`. Each constructs the widget offscreen and asserts its contract — signal
emitted with the right payload, visibility toggles, `add_*` returns, unknown role raises.

`shared/theme.py`'s `__main__` self-check already exercises `StatusDot`; it is updated for
the new signature and gains a `StatusChip` line. Both repos' gates run it.

Button roles get one test asserting `set_button_role` raises on an unknown name and that
`build_stylesheet` emits all four `[role="…"]` selectors. No screenshot tests — the QSS is
verified as text, and appearance is verified on Windows.

## 7. Acceptance

1. `StatusDot(role, theme)` resolves through `getattr`; `set_color` is gone; packing-tool's
   call site is updated and its gate passes.
2. `StatusChip` renders both variants and falls back to `surface_sunken` for a role with
   no `_bg` partner.
3. `BUTTON_ROLES` is the four roles; `build_stylesheet` emits all four attribute blocks;
   shopify's `role_stylesheet` contains only settingsNav rules and re-exports
   `set_button_role`; **no existing button changes appearance.**
4. The five `gui/components/` widgets exist with the APIs in §4 and a test file each.
5. Both gates pass: shopify `QT_QPA_PLATFORM=offscreen python -m pytest` + `ruff check .
   --exclude shared`; packing-tool per its own `CLAUDE.md`.
6. `sync_shared.py` leaves shopify's `shared/theme.py` byte-identical to packing-tool's.
